# RCA: Windows clones hang or come up unreachable at first boot

| | |
| --- | --- |
| Date | 2026-11-28 |
| Severity | Blocker for issue #4 (no usable Windows template) |
| Impact | Every clone of template 9001 `tpl-ws2022-core` never reached the network: no IPv4, no WinRM, no guest agent. Nothing downstream (AD, Ansible) could start. |
| Status | Resolved - all three templates rebuilt; smoke tests pass: 9001 in 84 s, 9002 in 109 s, 9003 in 413 s |

## Timeline

- Packer build of 9001 succeeds (7 min); sysprep reports `IMAGE_STATE_GENERALIZE_RESEAL_TO_OOBE`.
- Smoke-test clone VM 999 boots, but port 5986 stays closed for 20+ min and the guest agent never answers.
- Headless triage (no console used):
  - Proxmox `rrddata` shows ~10 % CPU for one minute, then ~1 % and near-zero disk I/O, i.e. idle, not looping.
  - `ip neigh show dev vmbr1` shows the VM's IPv6 link-local address, so Windows is up and the NIC works; only the IPv4 configuration is missing.
  - Together these point to Setup waiting at a modal dialog.
- The VM is stopped and `scripts/diag/win-offline-logs.sh` copies the Setup logs off the disk, read-only. **Cause 1 found.**
- Template rebuilt with fix 1: the clone reaches WinRM in 72 s, but comes up as `WIN-XXXX` instead of `HQ-TST01`. **Cause 2 found** in the cloudbase-init log, read over WinRM.
- Template rebuilt with fix 2: all 5 smoke checks pass.

## Root cause (5 whys)

### Cause 1: the answer file was rejected in the specialize pass

1. **Why did the clone not get an IP?** Windows Setup stopped at *"Windows could not parse or process unattend answer file [C:\Windows\Panther\unattend.xml] for pass [specialize]. The answer file is invalid."* (`setuperr.log`: `/settings/RunSynchronous/RunSynchronousCommand/[Order="1"]/Path`, *Value is invalid*, `0x80220005`).
2. **Why was it invalid?** `RunSynchronousCommand/Path` held a 467-character PowerShell one-liner. Windows Setup allows 259.
3. **Why did the build not catch it?** `sysprep /generalize` does not validate specialize-pass settings. The error only appears on the first boot of a clone.
4. **Why was the logic inline?** The network reset had been moved out of `sysprep.ps1` to fix an earlier bug and was put straight into the answer file.
5. **Why was it seen so late?** There was no lint for answer-file limits and no automated clone test before this incident.

### Cause 2: the hostname was never applied

1. **Why `WIN-XXXX`?** cloudbase-init logged `Hostname not found in metadata`.
2. **Why?** For Windows guests, Proxmox writes the hostname only to `user_data` (`#cloud-config`, `hostname: <vm name>`) and never to `meta_data.json` (`PVE::QemuServer::Cloudinit::cloudbase_configdrive2_metadata`).
3. **Why was user_data ignored?** The specialize-pass cloudbase-init config loaded only `SetHostNamePlugin`, which reads metadata. It did not load `UserDataPlugin`.

## Corrective / preventive actions

- [x] Move the network reset into `packer/windows/setup/reset-build-network.ps1`, called with `-File` (104 characters). It logs to `C:\Windows\Panther\reset-build-network.log`.
- [x] Add the `UserDataPlugin` to the specialize run with `cloud_config_plugins=hostname,set_hostname`. Only the hostname key is honoured; the Linux-oriented keys in Proxmox's user_data are ignored.
- [x] Preventive: `scripts/lint/check-unattend.py` pre-commit/CI hook. It fails when `<Path>` exceeds 259 or `<CommandLine>` exceeds 1024 characters, and it flags the old answer file.
- [x] Preventive: `scripts/smoke-test.sh`. It clones, boots and verifies every template from the outside before the template is accepted.
- [x] Runbook tool: `scripts/diag/win-offline-logs.sh` for clones that never reach the network.

## Follow-up: Windows 11 template 9003 (same day)

With causes 1 and 2 fixed, the server templates passed, but the first win11 clone never opened 5986. The guest agent worked on this clone, so the triage ran live through the Proxmox `agent/exec` API, again without a console.

### Cause 3: WinRM was not running yet

`winrm-https.log` showed *"WinRM service is not started currently ... Do you want to continue?"*, then *NonInteractive mode*. On client SKUs WinRM is a delayed-start service. The LocalScript touched `WSMan:\` before the service was up, and the provider tried to prompt.

### Cause 4: the network profile was Public

After WinRM was started by hand: *"WinRM firewall exception will not work since one of the network connection types on this machine is set to Public."* Client SKUs block WSMan service changes on Public networks, and the unattend `NetworkLocation` setting has been ignored since Windows 10.

### Cause 5: OOBE renamed the machine

The System event log recorded *"changed from PKR-BUILD to DESKTOP-SD3E7HP"* 30 s after cloudbase-init set `hq-tst01`. `UnattendGC\setupact.log` shows `msoobe.exe` ComputerName plugin: *Setting computer name to [DESKTOP-SD3E7HP]*. Only client OOBE does this.

### Actions

- [x] `winrm-https.ps1` starts WinRM and waits for it, then switches Public profiles to Private. Private suits the lab LANs, and a domain join later makes the profile DomainAuthenticated.
- [x] The cloudbase-init service run re-applies the hostname from user_data, ordered before the LocalScript. The reboot caused by the rename therefore happens before the WinRM certificate is issued.
- [x] All three templates rebuilt and re-tested, as a regression check, because the fixes touch shared files.

## Lessons

- A successful image build proves nothing about the first boot of a clone. Only a clone-boot-verify test does.
- Server and client SKUs differ in first-boot behaviour (service start, network profile, OOBE naming). Test every template, not one per family.
- Diagnose headlessly first: resource graphs, the neighbour table, offline logs and the guest-agent exec API found all five causes without a console session.
